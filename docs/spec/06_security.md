# מסמך דרישות אבטחת מידע וסייבר — "כמותן" (שלב 6)

גרסה 1.0, 11.10.2026. המסמך מבוסס על ה-PRD (01), תוכנית העבודה (02) ומסמך ה-stack. הוא מחייב את כל סוכני הפיתוח, ומשמש בסיס לבקרת PR רגישים ולבדיקת החדירה לפני הבטא (שלבים 9–10). ההערות המשפטיות אינן ייעוץ משפטי, ויש לאשר אותן מול עו"ד פרטיות לפני חתימה על חוזים עם לקוחות.

## תקציר ורמת סיכון

**מה אנחנו מגינים עליו.** סטי שרטוטים של לקוחות הם קניין רוחני של משרדי אדריכלות ועיצוב. טבלאות הכותרת כוללות שמות של בעלי בתים פרטיים, כתובות מגורים ולעתים טלפונים, ולכן זה **מידע אישי** לפי חוק הגנת הפרטיות. תוכנית של בית פרטי חושפת גם את מיקום החדרים, הפתחים, לוח החשמל ולפעמים מערכות אזעקה ומצלמות. במקרה של דליפה זה גם סיכון פיזי לדיירים.

**סיווג נתונים**

| רמה | דוגמאות | טיפול |
| --- | --- | --- |
| C3 – סודי לקוח | קבצי שרטוט מקוריים, אריחים, PDF מסומן, טבלת כותרת, טקסט OCR, כתבי כמויות, ספריית סעיפים ותבניות של הארגון | הצפנה, בידוד tenant, גישה רק דרך הרשאה, לא נשלח לצד שלישי ללא הסכם, לא נכנס ללוגים |
| C2 – אישי/תפעולי | אימייל ושם משתמש, IP, יומני ביקורת, נתוני חיוב | הצפנה, גישה מוגבלת לצוות, שמירה מוגבלת בזמן |
| C1 – פנימי | קוד, תצורה, מטריקות מצטברות | GitHub פרטי, ללא סודות בקוד |

**רמת סיכון כוללת: בינונית־גבוהה.** הגורמים: (1) multi-tenant, כך שכשל RLS אחד חושף את כל הלקוחות; (2) פענוח קבצים מורכבים ולא אמינים (PDF, DWG ו-DXF) בספריות C/C++, שזה משטח תקיפה קלאסי ל-RCE ול-DoS; (3) שליחת קטעי שרטוט לספקי LLM חיצוניים; (4) קישורי שיתוף חיצוניים; (5) פיתוח על ידי סוכני AI, שמגדיל את הסיכון לקוד לא בטוח ולדליפת סודות. אין במוצר מידע ביטחוני, רפואי או פיננסי רגיש, ופרויקטים מסווגים או ביטחוניים מחוץ להיקף ה-MVP (נכתב במפורש בתנאי השימוש). **יעד:** רמת אבטחה שקולה ל"רמה בינונית" בתקנות אבטחת מידע 2017, גם אם לא כל הוראותיה חלות עלינו פורמלית. עלות האבטחה צריכה להיכנס בתקציב התשתית הכולל של כמה מאות דולרים בחודש, ולכן מעדיפים כלים חינמיים ויכולות מובנות של הפלטפורמות.

**אזור נתונים:** Supabase ב-eu-central-1 (פרנקפורט). Workers ב-Cloud Run ב-europe-west או me-west1 (תל אביב), או ב-Railway באזור EU. Redis באזור EU. Sentry ב-EU data region ו-PostHog ב-EU Cloud. ב-Vercel יש רק נכסים סטטיים, ואין שם נתוני לקוח.

## דרישות אבטחה

עדיפות: **Must** נדרש לפני הבטא. **Should** מתוכנן ל-MVP, ואם נדחה הדחייה מתועדת.

### אימות (AuthN)

- **SEC-01 (Must)** — אימות דרך Supabase Auth: אימייל וסיסמה (מינימום 10 תווים ובדיקת סיסמאות שדלפו), magic link, ואופציונלית Google OAuth. Confirm email מופעל.
- **SEC-02 (Must)** — MFA מסוג TOTP **חובה** לתפקיד admin ולכל חשבון פנימי של הצוות, ורשות לשאר המשתמשים. האכיפה מתבצעת גם ב-RLS וב-API: פעולות ניהול (משתמשים, הגדרות ארגון, מתג LLM, מחיקה, ייצוא מלא) דורשות `aal = 'aal2'` ב-JWT.
- **SEC-03 (Must)** — תוקף access token עד שעה, refresh token rotation עם reuse detection, ויציאה מכל ההתקנים. אחרי איפוס סיסמה או שינוי תפקיד מבטלים את כל הסשנים.
- **SEC-04 (Must)** — הגנת כניסה: rate limit מובנה של Supabase, CAPTCHA (Turnstile, חינמי) בהרשמה ובשחזור סיסמה, והודעות שגיאה אחידות שלא חושפות אילו משתמשים קיימים.
- **SEC-05 (Should, שלב ב')** — SSO (SAML/OIDC) למשרדים גדולים, והגבלת דומיין הזמנה לכל ארגון.

### הרשאות ובידוד tenants

- **SEC-06 (Must)** — לכל טבלה עסקית יש עמודת `org_id NOT NULL` ו-RLS מופעל (`FORCE ROW LEVEL SECURITY`). המדיניות נשענת על פונקציית `is_member(org_id, min_role)` מסוג `SECURITY DEFINER` עם `search_path` קבוע. **בדיקת CI** נכשלת אם קיימת טבלה ב-schema `public` בלי RLS או בלי מדיניות.
- **SEC-07 (Must)** — מטריצת תפקידים:

| פעולה | admin | editor | reviewer | viewer |
| --- | --- | --- | --- | --- |
| ניהול משתמשים והגדרות ארגון ו-LLM | ✓ | — | — | — |
| יצירת פרויקט והעלאה | ✓ | ✓ | — | — |
| תיקון פריטים ושינוי סטטוס | ✓ | ✓ | ✓ | — |
| אישור שורה סופי | ✓ | ✓ | ✓ | — |
| ייצוא ויצירת קישור שיתוף | ✓ | ✓ | — | — |
| צפייה | ✓ | ✓ | ✓ | ✓ |
| מחיקת פרויקט / offboarding | ✓ (MFA) | — | — | — |

- **SEC-08 (Must)** — ה-API ב-NestJS ניגש ל-DB **בהקשר המשתמש**: מעביר את ה-JWT כך ש-RLS נאכף, ובנוסף מפעיל Guard מבוסס תפקיד. מפתח service_role מותר רק במודולים מוגדרים (מנהל תורים, offboarding, audit writer), מאחורי wrapper ייעודי עם רשימה סגורה של פעולות. כלל lint או Semgrep חוסם שימוש בו מחוץ לתיקיות האלה.
- **SEC-09 (Must)** — **בדיקות בידוד אוטומטיות** (ראו "בדיקות אבטחה"): לכל טבלה ולכל endpoint נבדק שמשתמש מ-org A לא יכול לקרוא, לעדכן, למחוק או להכניס רשומה עם org B.
- **SEC-10 (Must)** — מזהים הם UUID ולא מספרים רצים. כל endpoint שמקבל מזהה מאמת שייכות לארגון של המשתמש, וזו שכבת הגנה כפולה מעבר ל-RLS.
- **SEC-11 (Must)** — גישת תמיכה (צוות כמותן לנתוני לקוח) כבויה כברירת מחדל. היא ניתנת רק בהסכמה של admin בארגון, מוגבלת בזמן (למשל 72 שעות) ומתועדת ביומן הביקורת.
- **SEC-12 (Should)** — הרשאות ברמת פרויקט (חבר בארגון שלא משויך לפרויקט לא רואה אותו), כהגדרה אופציונלית לארגון.

### אבטחת העלאת קבצים

- **SEC-13 (Must)** — העלאה ישירה מהדפדפן ל-bucket בשם `quarantine` דרך signed upload URL ש-API מנפיק (TTL של 10 דקות, נתיב קבוע `org/{org_id}/upload/{uuid}`, ללא שם קובץ מהמשתמש בנתיב). שם הקובץ המקורי נשמר רק כ-metadata ועובר סניטציה.
- **SEC-14 (Must)** — אימות סוג הקובץ לפי **magic bytes** ולא לפי סיומת או Content-Type. מותרים רק: `%PDF-`, חתימת DWG `AC10xx`, DXF טקסטואלי (מבנה `0\nSECTION`) או בינארי, PNG. גודל עד 100MB לקובץ, עד 100 גיליונות ועד 2GB לפרויקט (ניתן להגדרה). כל דבר אחר נדחה.
- **SEC-15 (Must)** — סריקת נוזקות עם ClamAV (container עם חתימות מתעדכנות פעם ביום) לפני העברה מ-`quarantine` ל-`originals`. קובץ נגוע נמחק, המשתמש מקבל הודעה ונרשם אירוע ביומן.
- **SEC-16 (Must)** — הגנה מפצצות דחיסה: `Image.MAX_IMAGE_PIXELS` ב-Pillow מוגבל ל-‎≈200MP (A0 ב-300DPI הוא ‎≈140MP). מגבלה על יחס פריסה של streams ב-PDF, על מספר עמודים ועל מספר אובייקטים. אם ZIP יתקבל בעתיד: עד 500 קבצים, יחס דחיסה עד 1:100, ובדיקת path traversal (`..`, נתיבים מוחלטים, symlinks).
- **SEC-17 (Must)** — **sandbox לפענוח.** כל פענוח (PyMuPDF, ezdxf, ODA File Converter, OCR, רסטריזציה) רץ בתהליך נפרד בתוך container עם:
  - משתמש non-root, `readOnlyRootFilesystem`, תיקיית עבודה זמנית יחידה שנמחקת בסוף ה-job;
  - **ללא רשת**: network namespace ריק (nsjail או `unshare -n` כשאפשר), או שירות parser נפרד ב-Cloud Run עם egress שמנותב כולו ל-VPC וכלל firewall שחוסם הכל. ה-worker המתזמר (שיש לו רשת) מוריד את הקובץ ומעביר לתהליך הפענוח קובץ מקומי בלבד;
  - מגבלות: CPU 120 שניות לגיליון, זיכרון 2–4GB, זמן כולל ל-job (timeout), גודל פלט, ו-`RLIMIT_NPROC`;
  - ללא סודות במשתני הסביבה של תהליך הפענוח;
  - ב-PDF: JavaScript, embedded files, launch actions ו-URI לא מבוצעים לעולם. משתמשים רק בחילוץ גאומטריה וטקסט. ב-DXF מתעלמים מ-XREF ומקבצים חיצוניים.
- **SEC-18 (Must)** — ספריות הפענוח (PyMuPDF/MuPDF, Pillow, ezdxf, Tesseract, ODA) מקובעות לגרסה ומתעדכנות תוך 7 ימים מפרסום CVE קריטי. ODA File Converter הוא בינארי סגור, ולכן הוא רץ באותו sandbox ומוריד אותו רק מאתר היצרן עם checksum מאומת.

### אחסון והצפנה

- **SEC-19 (Must)** — כל ה-buckets פרטיים: `quarantine`, `originals`, `derived` (אריחים, OCR, PDF מסומן) ו-`exports`. מדיניות storage ב-RLS מגבילה גישה לנתיב שמתחיל ב-`org_id` של המשתמש. CI בודק שאין bucket ציבורי.
- **SEC-20 (Must)** — הורדה וצפייה עוברות רק דרך signed URL קצר: 5 דקות לאריחים (מתחדש אוטומטית במציג), 2 דקות להורדת מקור או ייצוא. ה-API מנפיק URL רק אחרי בדיקת הרשאה. `Content-Disposition: attachment` למקורות. אריחים מוגשים כ-PNG/WebP שנוצר בשרת, ו-PDF או SVG של משתמש אף פעם לא מוצגים inline בדומיין האפליקציה.
- **SEC-21 (Must)** — הצפנה בתעבורה: TLS 1.2 ומעלה בכל מקום, HSTS עם preload, Redis עם TLS וסיסמה (`rediss://`) ולא חשוף לאינטרנט (רשת פרטית ב-Railway, או Upstash עם TLS). חיבורי Postgres עם `sslmode=require`.
- **SEC-22 (Must)** — הצפנה במנוחה: AES-256 של Supabase ל-DB, ל-Storage ולגיבויים, וכנ"ל אצל ספקי ה-worker וה-Redis. **Should:** הצפנה ברמת שדה (pgsodium/Vault) לטוקנים של אינטגרציות עתידיות.
- **SEC-23 (Should)** — מטמון VLM לפי hash (מתוכנית העבודה) נשמר תחת `org_id` ולא משותף בין ארגונים, כדי למנוע דליפה דרך התאמת hash.

### ניהול סודות

- **SEC-24 (Must)** — סודות נשמרים רק ב-secret store של הפלטפורמה (Vercel env, Railway variables או GCP Secret Manager, ו-GitHub Actions secrets ל-CI). gitleaks רץ כ-pre-commit וב-CI, ו-GitHub push protection מופעל. ה-worker לא מקבל service_role: הוא מקבל **Postgres role ייעודי** עם הרשאות רק לטבלאות jobs ותוצרים, ובכל כתיבה חייב לציין `org_id` שתואם ל-job. ה-job ב-Redis מכיל רק מזהים, וה-worker מאמת אותם מול ה-DB לפני העבודה.
- **SEC-25 (Must)** — סביבות נפרדות לחלוטין: dev, staging ו-prod הם פרויקטי Supabase נפרדים עם מפתחות שונים. החלפת מפתחות (rotation) כל 90 יום ומיד אחרי עזיבה של אדם או חשד לדליפה. יש runbook לסיבוב מפתח service_role ומפתחות LLM.

### קישורי שיתוף חיצוניים

- **SEC-26 (Must)** — טוקן אקראי של 256 ביט (base64url). ב-DB נשמר רק ה-SHA-256 שלו. הקישור מוגבל לפרויקט ולגרסה ספציפיים, לקריאה בלבד ובלי גישה לקובץ המקור.
- **SEC-27 (Must)** — תוקף חובה: ברירת מחדל 14 יום, מקסימום 90. ביטול מיידי בידי editor או admin. רשימת קישורים פעילים לכל פרויקט, וביטול אוטומטי במחיקת פרויקט או ב-offboarding. **Should:** סיסמה או OTP באימייל לקישור.
- **SEC-28 (Must)** — סימן מים דינמי על אריחים ועל PDF בצפייה דרך קישור ("שותף עם {שם/אימייל} • {תאריך} • {link-id}"). אפשרות (ברירת מחדל: מופעלת) **להסתיר את טבלת הכותרת** בצפייה החיצונית.
- **SEC-29 (Must)** — rate limit לפי IP ולפי טוקן (למשל 60 בקשות בדקה), חסימה אחרי ניסיונות כושלים, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer` ו-`Cache-Control: no-store`. כל צפייה נרשמת ביומן (זמן, IP מקוצר, user-agent).

### טיפול בנתונים ב-LLM/VLM

- **SEC-30 (Must)** — רק ספקים עם חוזה API שמבטיח **שאין אימון** על הנתונים, עם retention מינימלי (zero-data-retention כשזמין) ועם endpoint ב-EU כשאפשר. רשימת הספקים מופיעה ברשימת ה-sub-processors. אסור להשתמש בממשקי צרכן (צ'אט).
- **SEC-31 (Must)** — **מזעור**: שולחים רק אזורים חתוכים (מקרא, תוויות חדרים, אזור טקסט ספציפי) ולא גיליון מלא. **טבלת הכותרת לא נשלחת לעולם ל-LLM**, וקריאתה נעשית ב-OCR מקומי בלבד. לפני שליחה מורידים metadata של הקובץ (שם קובץ, Author).
- **SEC-32 (Must)** — מתג לכל ארגון (FR-31): "כבה LLM חיצוני". כשהוא כבוי, הצנרת עוברת לחילופין מקומיים (OCR בלבד) והביטחון יורד בהתאם. ה-gateway (מודול יחיד שדרכו עוברות כל הקריאות) בודק את המתג **בכל קריאה** ולא רק כשה-job מתחיל. השינוי נרשם ביומן הביקורת.
- **SEC-33 (Must)** — הגנה מ-prompt injection: טקסט מהשרטוט מועבר כנתון תחום (delimited) ולא כהוראה. אין למודל כלים ואין לו גישת רשת. הפלט חייב להתאים ל-JSON schema קשיח שעובר ולידציה. ה-LLM **אף פעם** לא קובע הרשאות, סטטוס "אושר" או ביטחון ירוק. תוצרי LLM מקבלים לכל היותר רמת "סביר" עד אישור או כיול.
- **SEC-34 (Must)** — לוגים: אין לשמור prompts, תמונות או תשובות מלאות בלוגים, ב-Sentry או ב-OTel. נרשמים רק מזהה בקשה, מודל, מספר טוקנים, עלות ומשך. ב-Sentry מוגדרים `beforeSend` scrubbing ו-`sendDefaultPii=false`. ב-PostHog מכבים autocapture של טקסט ו-session replay, או מגדירים maskAllInputs ומסתירים את אזור השרטוט.

### יומן ביקורת

- **SEC-35 (Must)** — טבלת `audit_log` מסוג append-only: ל-roles של האפליקציה אין הרשאות `UPDATE` או `DELETE`, וכתיבה מתבצעת דרך trigger או פונקציה. כל רשומה כוללת `hash` שמשורשר לרשומה הקודמת (hash chain). אירועים: כניסה (הצלחה וכשל), MFA, שינוי תפקיד, הזמנה, העלאה, צפייה והורדה של מקור, ייצוא, יצירה, ביטול וצפייה בקישור שיתוף, שינוי מתג LLM או הסכמת אימון, גישת תמיכה, מחיקה ו-offboarding, ושינוי סטטוס שורה (FR-26). שמירה ל-24 חודשים לפחות, בהתאם לדרישת התקנות לרמה בינונית. ייצוא שבועי ל-bucket נפרד עם object lock או versioning. admin רואה את היומן של הארגון שלו.

### גיבוי והתאוששות (DR)

- **SEC-36 (Must)** — **RPO של 24 שעות ו-RTO של 8 שעות עבודה** ב-MVP. גיבוי יומי של Supabase (Pro), וגם `pg_dump` לילי מוצפן (age/GPG) ל-bucket באזור EU אחר בחשבון ענן נפרד, עם retention של 30 יום. **Should:** PITR (תוספת בתשלום) כשיש לקוחות משלמים, כדי להוריד את ה-RPO לדקות.
- **SEC-37 (Must)** — Storage: versioning או סנכרון לילי של `originals` ל-bucket גיבוי נפרד (נגזרות ניתן לשחזר מחדש מהמקור, ולכן אין צורך לגבות אותן).
- **SEC-38 (Must)** — תרגיל שחזור לפני הבטא ואחר כך פעם ברבעון, עם תיעוד הזמן בפועל.

### אבטחת ממשק ו-API

- **SEC-39 (Must)** — XSS: כל טקסט שמגיע מ-OCR, מ-DXF (שמות שכבות, בלוקים, מאפיינים) או מ-LLM מוצג רק כטקסט ב-React. `dangerouslySetInnerHTML` אסור (כלל lint). **Excel/CSV injection**: כל תא שמתחיל ב-`= + - @ \t \r` מקבל קידומת `'` בייצוא.
- **SEC-40 (Must)** — כותרות: CSP קשיח (`default-src 'self'`, `script-src 'self'` ללא inline/eval, `connect-src` רק ל-API, Supabase, Sentry ו-PostHog, `frame-ancestors 'none'`, `object-src 'none'`), `X-Content-Type-Options: nosniff`, `Permissions-Policy` מצומצם. מתחילים במצב Report-Only בספרינט 0 ועוברים ל-enforce לפני הבטא.
- **SEC-41 (Must)** — CSRF: האימות נעשה עם Bearer JWT בכותרת ולא עם cookie, ולכן CSRF לא רלוונטי. אם יוכנסו cookies, הם יהיו `SameSite=Strict`, `HttpOnly` ו-`Secure` עם CSRF token. CORS ב-API: allowlist מפורש של דומיין הפרונט בלבד, ללא `*` עם credentials.
- **SEC-42 (Must)** — Rate limiting ב-API (`@nestjs/throttler` עם Redis): לפי משתמש ולפי ארגון, ומגבלה מחמירה על העלאות, ייצוא, יצירת קישורים וקריאות שמפעילות LLM. מכסת עיבוד ועלות LLM לכל ארגון ביום, עם התראה בחריגה (הגנה מ-denial-of-wallet). ולידציה של כל DTO עם `class-validator` ו-`whitelist: true`.

### ניטור והתראות

- **SEC-43 (Must)** — התראות (Sentry alerts, דשבורד Supabase ו-cron פשוט שנשלח לאימייל או ל-Slack) על: קפיצה בכשלי כניסה; גישה שנדחתה ב-RLS או ב-Guard מעל סף; קובץ נגוע; job שחרג ממגבלות sandbox או קרס בסיגנל (סימן אפשרי לניצול); חריגת עלות LLM; צפיות רבות בקישור שיתוף; שימוש ב-service_role מחוץ לרשימה; שינוי הרשאות admin. לוגים מובנים (JSON) עם `org_id`, `user_id` ו-`request_id`, ללא תוכן קבצים. שמירת לוגים תפעוליים ל-30–90 יום.

### שרשרת אספקה ו-CI/CD

- **SEC-44 (Must)** — lockfiles מחויבים (`pnpm-lock.yaml`, ו-`uv.lock` או `requirements.txt` עם hashes). `npm ci` או התקנה מנועלת ב-CI. התקנות של ספריות חדשות עוברות בקרה ב-PR.
- **SEC-45 (Must)** — Dependabot (גרסאות ו-security alerts) ל-npm, pip, Docker ו-GitHub Actions. SCA ב-CI באמצעות `osv-scanner` ו-Trivy לאימג'ים, ו-PR נחסם על חולשה Critical או High שיש לה תיקון.
- **SEC-46 (Should)** — SBOM (CycloneDX דרך Syft) לכל release, שנשמר כ-artifact. חתימת commits אופציונלית. אימג'ים לפי digest ולא לפי `latest`, מבוססי slim/distroless.
- **SEC-47 (Must)** — branch protection על `main`: PR חובה, CI ירוק, אישור אחד לפחות, ללא force push, linear history. **CODEOWNERS** לנתיבים רגישים (`supabase/migrations`, `**/rls/**`, `auth`, `storage policies`, `.github/workflows`, `infra/`, sandbox של ה-worker, LLM gateway) מחייב גם **אישור אנושי** מבעל המוצר או מבעל תפקיד אבטחה.
- **SEC-48 (Must)** — GitHub Actions: `permissions: contents: read` כברירת מחדל ברמת workflow. Actions של צד שלישי מקובעות ל-commit SHA. אין `pull_request_target` עם checkout של קוד ה-PR. סודות פרודקשן נמצאים רק ב-environment `production` עם required reviewers.
- **SEC-49 (Must)** — פריסה עם **OIDC** ל-GCP (Workload Identity Federation) בלי מפתחות JSON קבועים. ב-Vercel וב-Railway: טוקן מוגבל לפרויקט, שנשמר ב-environment מוגן. מיגרציות לפרודקשן רצות רק מ-workflow מאושר ולא ממחשב של מפתח או של סוכן.
- **SEC-50 (Must)** — SAST: Semgrep CE (חוקי TypeScript, NestJS, Python ו-React, יחד עם חוקים מותאמים ל-service_role ול-`dangerouslySetInnerHTML`), Bandit ל-Python ו-gitleaks. הכלים רצים על כל PR.

### שמירה ומחיקה של נתונים

- **SEC-51 (Must)** — מדיניות שמירה: קבצים ונגזרות נשמרים כל עוד הארגון פעיל. פרויקט שנמחק עובר ל-soft delete ל-30 יום ואז נמחק לצמיתות, כולל storage ומטמון VLM. הנתונים נמחקים מהגיבויים במחזור הגיבוי (עד 30 יום נוספים), וזה מוצהר ב-DPA. ה-PRD קובע "שום דבר לא נמחק" ברמת גרסאות, וזה תקף רק בזמן שהפרויקט פעיל.
- **SEC-52 (Must)** — **Offboarding של ארגון**: (1) ייצוא מלא ללקוח (ZIP של מקורות וכתבי כמויות ו-JSON); (2) ביטול כל הקישורים והסשנים; (3) מחיקה קשה של DB ו-storage תוך 30 יום; (4) תעודת מחיקה ללקוח; (5) רשומת audit מצומצמת (ללא תוכן) נשמרת לצורכי ראיה. התהליך כולו כתוב כסקריפט עם בדיקה אוטומטית.

### הגבלות לסוכני AI מפתחים

- **SEC-53 (Must)** — סוכנים **לעולם לא** מקבלים סודות פרודקשן, גישה ל-Supabase prod, למסוף Vercel, Railway או GCP של prod, או נתוני לקוח אמיתיים. הם עובדים רק מול dev או staging עם נתונים סינתטיים או אנונימיים.
- **SEC-54 (Must)** — שרטוטי "בית משפחת נח" ופרויקטי השותפים לא נכנסים ל-Git. ה-benchmark נשמר ב-bucket פרטי ונפרד, ולסוכנים ניתנות רק גרסאות שבהן טבלת הכותרת עברה אנונימיזציה, אחרי הסכמה בכתב של בעל השרטוט.
- **SEC-55 (Must)** — טוקני GitHub של סוכנים הם fine-grained ומוגבלים לריפו, עם הרשאת contents ו-PR בלבד. בלי admin, בלי שינוי branch protection ובלי merge עצמי. כל PR נסקר בידי סוכן אחר. PR בנתיבי CODEOWNERS (SEC-47) או PR שמוסיף תלות חדשה דורש גם אישור אנושי. פלט סוכנים בלוגים של CI לא כולל סודות (masking).

## פרטיות ועמידה ברגולציה

**תפקידים לפי החוק.** כלפי שרטוטי הלקוחות, הלקוח (המשרד) הוא **בעל מאגר** ו"כמותן" היא **מחזיק** (processor) שפועל לפי הוראותיו. כלפי מאגר המשתמשים שלה עצמה (חשבונות, חיוב, אנליטיקה) "כמותן" היא בעל המאגר.

**תיקון 13 (בתוקף מ-14.8.2025): מה רלוונטי לנו**

- **רישום מאגר:** אחרי התיקון חובת הרישום מצומצמת בעיקר למאגרים שמטרתם העיקרית מסירת מידע לאחרים כעיסוק (סוחרי מידע) מעל סף של כ-10,000 נושאי מידע, ולגופים ציבוריים. **הערכה: "כמותן" לא חייבת ברישום.** קיימת **חובת הודעה** לרשות על מאגר עם מידע בעל רגישות מיוחדת על 100,000 איש ומעלה. שמות וכתובות בטבלת כותרת אינם כשלעצמם "רגישות מיוחדת", ולכן גם זה לא צפוי לחול ב-MVP. ההערכה נבחנת מחדש בכל רבעון ובכל שינוי היקף.
- **ממונה הגנת פרטיות (DPO):** חובה לגופים ציבוריים, לסוחרי מידע ולמי שעיקר פעילותו ניטור שיטתי בהיקף ניכר או עיבוד מידע רגיש בהיקף ניכר. **הערכה: לא חובה.** מומלץ למנות **ממונה אבטחת מידע** (חובה ברמה בינונית במקרים מסוימים) ואחראי פרטיות פנימי, שיכול להיות המייסד, עם 2–4 שעות בחודש של יועץ חיצוני.
- **חובת יידוע ושקיפות:** מדיניות פרטיות בעברית שמפרטת מטרות, ספקים, העברה לחו"ל והסכמת אימון. הלקוח (בעל המאגר) אחראי ליידע את בעלי הבתים, ו-DPA מחייב אותו בכך.
- **זכויות נושא מידע:** עיון (סעיף 13) ותיקון (סעיף 14). כמחזיק, מעבירים בקשות לבעל המאגר ומספקים כלים: חיפוש לפי שם או כתובת בטקסט OCR של הארגון, ייצוא ומחיקה. SLA פנימי: 14 יום.
- **אירוע אבטחה חמור:** לפי תקנות 2017, בעל מאגר מדווח לרשות להגנת הפרטיות **מיד**. מחזיק מדווח לבעל המאגר מיד. ב-DPA אנו מתחייבים להודיע ללקוח **תוך 24 שעות** מגילוי, עם פרטי האירוע, ההיקף והצעדים שננקטו. כך הלקוח יכול לעמוד בחובותיו, וגם הודעה לנושאי מידע אם הרשות תורה עליה.
- **אכיפה:** התיקון מעניק לרשות סמכויות פיקוח ועיצומים כספיים משמעותיים. לכן נדרשים תיעוד (נוהל אבטחה, מיפוי מאגר, סקר סיכונים) ובקרה שנתית.

**תקנות אבטחת מידע 2017.** אנו מיישמים מרצון את דרישות **הרמה הבינונית**: מסמך הגדרות מאגר, נוהל אבטחה, ניהול הרשאות לפי צורך, יומן גישה ששמור 24 חודשים (SEC-35), סקר סיכונים, בקרה כל 18 חודשים לפחות, הסכם מחזיק בכתב (תקנה 15), הדרכת עובדים ותיעוד אירועים.

**העברה לחו"ל.** אחסון ועיבוד ב-EU מותרים לפי תקנות העברת מידע למאגרים מחוץ לגבולות המדינה (2001), כי דיני ה-EU מבטיחים הגנה שאינה פחותה. ספקי LLM בארה"ב: מתירים רק עם התחייבות חוזית לאי-אימון, ל-retention מינימלי ולאבטחה (DPA ו-SCC), בהסכמת הלקוח דרך רשימת sub-processors ועם המתג SEC-32. מעדיפים endpoints ב-EU.

**DPA עם לקוחות.** סעיפי חובה: הגדרת תפקידים, מטרות העיבוד, הוראות בעל המאגר, סודיות של הצוות, אמצעי אבטחה (נספח שנגזר ממסמך זה), sub-processors עם הודעה מראש של 30 יום על שינוי וזכות התנגדות, דיווח אירוע תוך 24 שעות, סיוע בזכויות נושאי מידע, מחיקה או החזרה בסיום (SEC-52), זכות ביקורת (שאלון או דו"ח), איסור שימוש למטרות אחרות פרט לאימון ב-opt-in.

**הסכמה לאימון (FR-33)**

- כבוי כברירת מחדל. ההפעלה נעשית רק בידי admin, עם טקסט הסכמה מפורש, גרסה, תאריך ושם המאשר ביומן. אפשר לבטל בכל עת, וביטול חל על אימונים עתידיים: הנתונים יוצאים מסט האימון בגרסה הבאה.
- **אנונימיזציה לפני כניסה לסט אימון:** מזהים את טבלת הכותרת (FR-07) ומשחירים אותה כולה, כולל לוגו, שמות, כתובת, טלפון, מספר גוש וחלקה ומספר היתר. כנ"ל לטקסט חופשי עם תבניות של טלפון, אימייל, ת"ז וכתובת. מסירים metadata של הקובץ ושמות קבצים. בודקים אנושית מדגם של 10% לפני שימוש. נתוני אימון נשמרים ב-bucket נפרד ללא קישור ל-org.
- גם אחרי אנונימיזציה, תוכנית בית ייחודית יכולה לשמש לזיהוי מחדש. לכן נתוני אימון משמשים רק למודלים פנימיים, ולא נמסרים או מפורסמים.

## תגובה לאירועים

**חומרה:** **SEV1**: חשד לגישה לנתוני ארגון אחר, דליפת סודות, RCE ב-worker או כופרה. **SEV2**: חולשה מנוצלת בלי עדות לדליפה, קישור שיתוף שדלף או חשבון admin שנפרץ. **SEV3**: חולשה שדווחה ולא נוצלה או נוזקה שנחסמה.

**תפקידים:** מנהל אירוע (המייסד או בעל תפקיד האבטחה, אדם ולא סוכן), אחראי טכני, ואחראי תקשורת ומשפט (עם עו"ד פרטיות בכוננות). סוכני AI יכולים לסייע בניתוח לוגים רק בסביבה מבודדת, ללא סודות.

**שלבים**

1. **זיהוי ורישום** — פתיחת ticket פרטי ותיעוד ציר זמן מהדקה הראשונה.
2. **בלימה (עד שעה ב-SEV1)** — ביטול סשנים ומפתחות שנפגעו (סיבוב service_role, מפתחות LLM ו-Redis), השבתת קישורי שיתוף, עצירת workers או מתג LLM גלובלי, חסימת IP, ומצב תחזוקה אם צריך.
3. **שימור ראיות** — snapshot של DB ולוגים, ייצוא audit_log, ולא מוחקים כלום.
4. **הערכת היקף** — אילו ארגונים, אילו נתונים (C3 או C2) וכמה נושאי מידע.
5. **הודעות** — ללקוחות שנפגעו **תוך 24 שעות** (DPA), כדי שבעל המאגר ידווח לרשות להגנת הפרטיות מיד באירוע חמור. סיוע בהודעה לנושאי מידע כשנדרש, ודיווח לספקים רלוונטיים.
6. **מיגור ושחזור** — תיקון, פריסה, ושחזור מגיבוי אם צריך (RTO של 8 שעות).
7. **לקחים תוך 5 ימי עבודה** — ניתוח ללא האשמה, עדכון מודל האיומים, דרישות SEC ובדיקות רגרסיה.

**הכנה:** דף אנשי קשר (ספקים, עו"ד, הרשות), runbooks לסיבוב כל סוג סוד, תבנית הודעה ללקוח בעברית, ו-`security.txt` עם כתובת לדיווח חולשות. תרגיל שולחני אחד לפני הבטא.
